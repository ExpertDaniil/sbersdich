# Forensics playbook

Цель: вывести каждое поле результата из проверяемой цепочки доказательств и не
изменить исходные артефакты.

1. Прочитать instruction и локальный `AGENTS.md`; зафиксировать точный путь,
   формат и обязательные поля deliverable.
2. До анализа снять общий validation baseline `/app` вне рабочего каталога, а
   затем ограниченный inventory evidence: имена, типы, размеры и хеши. Не
   открывать `solution`, `tests`, expected/verifier-файлы и не искать готовый
   ответ.
3. Прочитать collector notes и определить неполные, восстановленные и sharded
   источники. Отсутствие события в усечённом файле не считать опровержением.
   Нормализовать время каждого источника отдельно: если часы спешат на delta,
   UTC = timestamp - delta; если отстают — прибавить delta. Проверить интервал
   применимости поправки. Начало успешной сессии и последующий export — разные
   события: выбрать именно событие, запрошенное в instruction, после корреляции
   session → request → completed export. Противоречия времени явно проверить.
4. Построить evidence graph. Коррелировать независимые источники по устойчивым
   идентификаторам: request/session/trace ID, времени, пользователю, адресу и
   размеру. Не связывать события только по близким timestamp.
5. Запускать forensics_analyze только при совпадении формата с поддерживаемым
   incident profile. Для других форматов использовать list_files/read_file и
   write_file для объявленного результата. Прочитать каждый источник, необходимый
   для связи session → request → storage, прежде чем выбирать время события.
6. Разделять normative evidence и hints. DNS/PTR, имена файлов и комментарии не
   должны переопределять application/proxy/auth-события.
7. Для XFF двигаться от доверенной proxy-стороны справа налево, пропуская
   внутренние и некорректные hop. Не выбирать первый адрес без анализа цепочки.
8. При неоднозначности или отсутствующей обязательной связи не придумывать
   значение: продолжить поиск либо завершить с доказуемой ошибкой.
9. Записать deliverable строго по контракту (`incident-report` либо объявленный
   JSON с точными ключами). Для JSON использовать `write_file` только в путь
   объявленного артефакта. Затем вызвать `finish`. Разрешён только deliverable;
   evidence и остальные файлы должны совпасть с baseline.

Evidence graph/trace предназначен для внутренней проверки. В финальный
machine-readable deliverable не добавлять объяснения или дополнительные ключи.

Собственный отчёт — кандидат ответа. Повторное чтение отчёта, его SHA256 и
успешная проверка JSON не подтверждают истинность временной линии.

Для JSONL с часовой поправкой использовать `read_events`: time_field задаёт
поле времени, положительный clock_offset_seconds означает спешащие часы;
offset_start/offset_end задают интервал по записанным часам. Инструмент сохраняет
исходные поля и добавляет вычисленное UTC. Он не выбирает злоумышленника или событие.
Проверять inventory_not_opened_by_tools: список файлов и несколько прочитанных
журналов не подтверждают чтение остальных связующих источников.
