# C-03 — ручной разбор и исправление SQL-инъекции в login

## Причина дефекта

`POST /login` получает `req.username` и `req.password` из тела HTTP-запроса. Оба значения напрямую вставлялись в SQL через f-string, после чего итоговая строка передавалась в `conn.fetchrow(query)`.

Цепочка данных:

`LoginRequest → req.username / req.password → f-string SQL → asyncpg.fetchrow()`

Значение вроде `admin'--` завершает строковый литерал и превращает остаток запроса в комментарий. Это позволяет исключить проверку пароля и обойти аутентификацию.

## Исправление

Запрос заменён на параметризованный вариант asyncpg:

```python
row = await conn.fetchrow(
    "SELECT id FROM users WHERE username = $1 AND password = $2",
    req.username,
    req.password,
)
```

Теперь SQL-команда и данные передаются драйверу отдельно. Кавычки, комментарии и логические выражения внутри username/password больше не меняют структуру SQL.

## Почему изменение минимально

- изменён только уязвимый запрос;
- endpoint, модели и формат ответа сохранены;
- успешная авторизация по-прежнему возвращает `token-{id}`;
- неверные данные по-прежнему дают HTTP 401;
- новые зависимости не добавлены;
- схема базы данных не изменена.

## Выполненные проверки

Автономный `verify.sh` проверяет:

1. компиляцию изменённого Python-файла;
2. наличие одного вызова `fetchrow` с постоянным SQL и двумя отдельными параметрами;
3. сохранение успешного входа `admin / secret123`;
4. отклонение неправильного пароля;
5. отклонение payload `admin'--`;
6. отклонение payload `admin' OR '1'='1`;
7. передачу вредоносных строк как данных, а не как части SQL.

Полный интеграционный прогон в среде организаторов:

```bash
cd /app
pytest tests/
```

Публичный verifier дополнительно перезапускает приложение из изменённого кода и проверяет штатные операции поиска, CRUD, комментариев, тегов и пользователей.
