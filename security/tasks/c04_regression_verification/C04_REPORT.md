# C-04 — регрессионная проверка SQLi-исправления

## Цель

Подтвердить две независимые вещи:

1. SQL-инъекция в `POST /login` больше не даёт HTTP 200.
2. После исправления сохранена обычная функциональность FastAPI-приложения.

Особое требование — тестировать процесс, запущенный после изменения файла. Уже работающий Uvicorn может продолжать исполнять старый импортированный код и создать ложный результат.

## Матрица проверок

| Проверка | Ожидаемый результат |
|---|---|
| `GET /healthz` | HTTP 200 и `{"status":"ok"}` |
| правильный login | HTTP 200 и непустой token |
| неправильный пароль | HTTP 401 |
| username `admin'--` | не HTTP 200 |
| username `admin' OR '1'='1` | не HTTP 200 |
| поиск `timeout` | возвращается `Fix login timeout` |
| фильтр `status=open` | все элементы имеют статус open |
| create/update/delete | полный CRUD проходит, после delete — 404 |
| комментарии | чтение и создание работают |
| теги | присутствует базовый тег `bug` |
| пользователи | минимум три записи, поле password не раскрывается |

## Как runner исключает проверку старого кода

`run_in_acp.sh`:

1. завершает процессы, соответствующие `[u]vicorn main:app`;
2. при необходимости пересоздаёт тестовую базу через `C04_RESET_DB=1`;
3. запускает Uvicorn из текущего `$APP_DIR`;
4. ждёт успешный `/healthz` и следит, что новый PID не завершился;
5. запускает тесты проекта;
6. отдельно запускает HTTP security/regression suite;
7. сохраняет логи и JSON-отчёт;
8. завершает только запущенный им процесс через trap.

## Запуск в runtime организаторов

Сначала применить исправление C-03 к учебной задаче. Затем поместить этот пакет в контейнер и выполнить:

```bash
C04_RESET_DB=1 ./run_in_acp.sh /app
```

Если приложение и подготовленная база уже запущены под непривилегированным пользователем:

```bash
./run_in_acp.sh /app
```

Результаты появятся в `results/`:

- `run.log`;
- `app.log`;
- `pytest.log`;
- `http_report.json`.

Успехом считается только exit code 0 при одновременном прохождении project pytest и 11 независимых HTTP-проверок.

## Локальная проверка самого пакета

`verify_package.sh` запускает fake HTTP API на случайном локальном порту и проверяет два сценария:

- безопасный login проходит все 11 проверок;
- намеренно уязвимый login обнаруживается ровно двумя SQLi-проверками.
- полный shell-runner запускает новый процесс, дожидается healthcheck и возвращает успех только при прохождении обеих групп тестов;
- провал project pytest корректно делает общий прогон неуспешным, даже если HTTP-проверки прошли.

Fake API используется только для проверки корректности тестового инструмента. Он не заменяет финальный прогон FastAPI/PostgreSQL в `secureintelligent/acp`.

### Фактический результат проверки пакета

- автономные тесты: 4 из 4 пройдены;
- безопасный fake API: 11 из 11 HTTP-проверок;
- намеренно уязвимый login: обе SQLi-проверки обнаружили дефект;
- полный runner: корректно запускает новый процесс и возвращает exit code 0;
- искусственный провал project pytest: общий runner корректно возвращает exit code 1;
- `py_compile`, `bash -n` и `sh -n`: пройдены;
- полный набор успешно повторён несколько раз.

В среде подготовки отсутствует Docker/PostgreSQL, поэтому финальное подтверждение на настоящем FastAPI-приложении остаётся отдельным запуском в `secureintelligent/acp`. Runner и критерии для него полностью подготовлены.
