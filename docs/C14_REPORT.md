# C14 — подключение CTF к production scaffold

База: `test_govno@5c2a7a4f9f0b0fb68fae7f1cabf40b90bb3b7e31`.
Отдельная ветка: `security/c14-ctf-integration`.

## Что сделано

Перенесены C13-компоненты из `main`: распознавание CTF-инструкции, извлечение
пути ответа, playbook, ограниченные преобразования данных, режим инструментов,
политика изменения файлов и тестовые вариации. Новые зависимости не нужны.

Добавлен `agent/core/ctf_completion.py`. Старый `AgentLoop` и production
`LegacyTaskVerifier` используют одну CTF-проверку завершения. Успех возможен,
только если общая проверка файлов прошла, инструкция задаёт выходной файл,
каждый ответ изменился в текущем запуске и для каждого пути есть успешное
событие `write_exact_text`. Путь берётся из фактического результата инструмента,
с нормализацией `/app`, абсолютных путей и Windows-алиасов.

Это проверка создания ответа и соблюдения правил, а не доказательство
правильности неизвестного флага. Правильность ответа оценивает независимый
verifier конкретной задачи.

В CTF отключена общая проверка синтаксиса исходного Python: материалы задания
могут содержать обрывки кода. Для остальных режимов поведение сохранено.
Изменение исходных доказательств приводит к провалу финальной проверки.

В ACI добавлен явный CTF-набор `view_window`/`search_surface`. Без этого
изменения незнакомый режим получал общий набор, включая `checked_edit`.
Проверка production-каталога воспроизводит эту проблему и подтверждает её
устранение. В CTF не предлагаются `apply_patch`, `run_command`, `run_check`,
`checked_edit` и `arena_promote`.

Перенесено исправление Windows-путей из `b39fffa`: `WorkspaceFileProvider`
нормализует рабочий каталог до вычисления относительных путей. Добавлен
соответствующий тест совместимости.

## Как это связано с кодом команды

Используется существующая цепочка `run.sh` → `agent.scaffold.cli` →
`build_default_application` → `LegacySecurityProvider` → наши ИБ-инструменты.
Новый агентный цикл или отдельный runtime не добавлялись. Сохраняются текущие
Repository Distiller, ACI, Candidate Arena, планировщик и сборщик архива.

В поставке два патча, оба относятся к одной тестовой ветке:

1. `sbersdich-c14-security.patch` — ИБ-код, C13/C14-тесты и этот отчёт.
2. `sbersdich-c14-scaffold.patch` — небольшой стык с каркасом, выделенный
   отдельно для просмотра его владельцем. Он меняет только:
   - `agent/scaffold/verifier.py`: общая CTF-проверка и выбор проверки синтаксиса;
   - `agent/scaffold/aci.py`: одна строка с CTF-набором операций;
   - `agent/scaffold/providers.py`: нормализация Windows-пути.

**Для полной проверенной версии нужны оба патча.** Первый отдельно не означает
завершённую интеграцию. Готовые изменения проверялись в отдельной локальной
копии. Удалённая тестовая ветка создана на исходном коммите; загрузку кода
выполняет пользователь. `test_govno`, `main` и репозиторий организаторов
не изменялись.

Всего в перечисленных unit/integration suites: 243 успешных теста и один
пропуск по платформе. C14-проверки входят в `agent/tests`, повторно прибавлять
их к этому числу не нужно. На Windows набор платформенных пропусков может
отличаться; POSIX `run.sh` проверяется на Linux, а упакованный Python CLI —
на обеих платформах.

Новые проверки проходят через production-композицию, а не только через старый
цикл. Проверяются отсутствие ответа, старый ответ, незарегистрированная запись
второго артефакта, недопустимое изменение доказательств, внешний путь,
кириллица и пробелы в путях, корректный ответ при повреждённом Python-фрагменте.

Архив собирается штатным сборщиком и распаковывается отдельно от проекта
задания. Проверяется совпадение `run.sh` с production-файлом, executable mode,
наличие CTF-кода и отсутствие тестов/`evaluation` в ZIP. В отдельном процессе
агент получает действия через loopback OpenAI-совместимый HTTP-симулятор.
Симулятор читает фактические наблюдения инструментов и задаёт заранее известную
стратегию; ожидаемый флаг используется только независимой проверкой теста.
Это проверяет интеграцию, **не качество настоящей LLM**. Симулятор не входит
в submission ZIP и не требует внешнего интернета.

Две официальные SQL-fix задачи также запускались через собранный архив:
агент изменил соответствующие `routers/auth.py` и `routers/items.py`.
Их PostgreSQL-verifier **не запускался**. Docker/ACP/Harbor и настоящий
локальный LLM endpoint в среде этой проверки недоступны. Публичной официальной
CTF-задачи в текущем репозитории организаторов нет.

## Проверка на компьютере участника

Из корня репозитория в PowerShell, после применения обоих патчей:

```powershell
& "C:\Program Files\Git\bin\bash.exe" "./scripts/check_all.sh"
& "C:\Program Files\Git\bin\bash.exe" "./evaluation/verify.sh"
git diff --cached --check
```

Оба скрипта обнаруживают новые тесты автоматически. Их старые итоговые подписи
с номерами C06/C11/C12 сохранены, чтобы не редактировать общий запуск команды.

Только C14-проверки, если Python доступен как `python`:

```powershell
python -m unittest discover -s agent/tests -p "test_c14*.py" -v
```

Полные команды применения, создания коммита и push находятся в инструкции
рядом с патчами. Применять их нужно в `security/c14-ctf-integration`.

## Что относится к следующим этапам

C14 не добавляет обязательный запуск тестов приложения после SQL-fix — это C15.
Не меняет правила восстановления планировщика после неудачного профиля,
общий бюджет токенов и финальный Docker/Harbor runner. Для официального
подтверждения двух SQL-fix задач нужен прогон с PostgreSQL. До финальной
отправки также нужен отдельный прогон с настоящей локальной моделью.
