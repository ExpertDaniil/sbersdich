# C15: обязательная проверка проекта после security-fix

## Что изменилось

До C15 агент мог исправить поддерживаемую SQL-инъекцию, получить чистый результат
сканирования и завершиться без запуска штатных тестов приложения. В двух публичных
fix-задачах организаторов корневой `AGENTS.md` требует выполнить `pytest tests/`
после изменения кода и считать работу законченной только после успешной проверки.

Теперь команда тестирования фиксируется до редактирования проекта. На каждом
`finish` в режиме `fix` агент проверяет синтаксис и допустимость изменений, запускает
зафиксированную suite, затем повторно проверяет состояние файлов. Падение теста,
ошибка запуска, отсутствие pytest, отсутствие собранных тестов или timeout не дают
объявить успех. Причина и ограниченный вывод команды возвращаются планировщику.

После исправления причины следующий `finish` снова проверяет текущий проект.
Успех прежнего `run_check` или Candidate Arena не заменяет финальную проверку.

## База и изоляция

- Рабочая ветка: `security/c15-fix-validation`.
- C14 вместе с исправлением CRLF: `d47aa2f63346c6e03911a221736c0fc907e60121`.
- Подтянутые коммиты команды из `test_govno`: до `ce6d453856195d08dc8a19b6f404656e7b8c9a62`.
- База отдельного патча C15 после объединения: `8e2f814741eabe8112a68cd2b375966046052bca`.
- Объединение не имело конфликтов. Логика hypothesis controller и state сохранена.
- Публикация C15 выполняется только в отдельную ветку. `main`, `test_govno`,
  ветка C14 и репозиторий организаторов не изменяются.

В общих scaffold-файлах сделаны только необходимые подключения: поле остатка
времени в `VerificationContext` с совместимым значением по умолчанию, передача
этого значения из kernel и вызов общей проверки из verifier. Архитектура команды,
планировщик, Candidate Arena и инструменты работы с репозиторием не переписывались.

## Как соединены компоненты

| Файл | Назначение |
| --- | --- |
| `agent/core/project_checks.py` | Определяет pytest-команды из instruction и корневого `AGENTS.md`; сохраняет их в неизменяемом плане. |
| `agent/core/models.py`, `agent/core/contracts.py` | Добавляют план проверок в `TaskContract` до начала действий агента. |
| `agent/core/fix_validation.py` | Запускает финальные проверки с ограничением времени, сохраняет вывод и контролирует изменения тестов/настроек. |
| `agent/core/loop.py` | Подключает ту же проверку к основному циклу. |
| `agent/scaffold/contracts.py`, `kernel.py`, `verifier.py` | Подключают проверку к production scaffold и передают остаток времени. |
| `agent/playbooks/fix.md` | Объясняет агенту условие завершения и поведение при ошибке. |
| `agent/tests/test_c15_project_checks.py` | Проверяет контракт, запуск, отрицательные сценарии и интеграцию. |
| `scripts/verify_c15.py`, `scripts/verify_c15.sh` | Отдельная проверка C15 с обязательным наличием настоящего pytest. |

## Контракт и ограничения

- Автоматически поддерживаются `pytest ...` и `python/python3 -m pytest ...`.
  Команды извлекаются из inline code и отдельных строк, включая fenced blocks.
- При отсутствии явной команды наличие Python-тестов в `tests/` включает запуск
  этой папки. Если поддерживаемой suite нет, это явно отмечается в отчёте;
  такой результат не является доказательством прохождения скрытых тестов.
- Используется Python из `.venv/bin/python` или `.venv/Scripts/python.exe`, если
  он существует, иначе текущий Python агента. Зависимости не устанавливаются.
- Сохраняется путь к Python виртуальной среды, а не цель его symlink.
- Запуск идёт списком аргументов с `shell=False`. Shell-операторы, внешние пути,
  `--collect-only`, `--ignore` и неподдерживаемые опции не выполняются автоматически.
- Не более четырёх различных обязательных команд; обычный timeout каждой — 60 с,
  дополнительно ограниченный оставшимся временем задачи. Проверка учитывает время
  статической валидации и не засчитывает завершение после исчерпания бюджета.
- Вывод читается как UTF-8 с заменой повреждённых байтов; в отчёт попадает до 4000
  байт начала/конца вывода плюс метаданные команды. Вывод собирается во временный
  файл вне проекта, чтобы избежать переполнения памяти и зависания на pipe.
- На Linux завершается отдельная группа процессов проверки, включая дочерние
  процессы. На Windows завершается непосредственный процесс; это не полноценная
  песочница процессов Windows. Целевой runtime соревнования — Linux-контейнер.
- Тесты, явно выбранные файлы/каталоги suite, `AGENTS.md`, `conftest.py`, `pytest.ini`
  и другие защищённые настройки проверяются до и после запуска. Их изменение
  блокирует результат; C15 не откатывает изменения автоматически.
- В дочерний pytest не передаются ключ и настройки LLM, а также внешние
  `PYTEST_ADDOPTS`, которые могли бы незаметно изменить набор тестов.
- C15 не запускает PostgreSQL/API и не переустанавливает зависимости. Подготовка
  этих сервисов принадлежит runtime; ошибки соединения будут видны в отчёте.

## Проверки

Среда проверки: Linux, Python 3.12, локальная среда разработки с pytest 9.1.1.
Нативный Windows-прогон здесь недоступен. CRLF и пути с кириллицей/пробелами
проверяются явными данными; существующие исправления Windows из C14 сохранены.

| Набор | Результат |
| --- | --- |
| C03 | 5 тестов успешно |
| C04 package | 4 теста успешно |
| C05 | 7 тестов успешно |
| Agent, включая C14, C15 и новые тесты команды | 212 тестов: 211 успешно, 1 Windows-тест пропущен на Linux |
| Evaluation | 51 тест успешно; portability 9/9 |
| Отдельная проверка C15 | 27 тестов успешно; они входят в agent-набор выше |

Итого: 279 обнаруженных unittest-тестов, 278 успешных, один платформенный пропуск.
Сквозные проверки запускают настоящий pytest на собственном небольшом SQL-fixture
с SQLite и адаптером вызова `fetchrow`. Проверяются обычный вход, неверный пароль и
инъекция. До исправления fixture падает, после исправления оба runtime проходят
тесты. Независимая регрессия блокирует успех при чистом security scan; после ремонта
повторная проверка проходит. Также проверен запуск CLI из извлечённого submission ZIP.

Эти результаты не являются оценкой закрытого бенчмарка или новым официальным 6/6.
Полный прогон двух SQL-задач организаторов требует ACP с PostgreSQL и работающим
API; он остаётся задачей C16. Реальная локальная LLM в проверках C15 не использовалась.

## Как проверить

Из корня репозитория в среде с уже установленным pytest:

```sh
bash scripts/verify_c15.sh
bash scripts/check_all.sh
bash evaluation/verify.sh
```

`verify_c15.sh` возвращает код 2, если pytest недоступен: расширенная проверка не
должна выглядеть успешной из-за пропуска интеграционных тестов. Для разработки
можно установить pytest заранее в локальную Python-среду или использовать среду
с уже установленными зависимостями. Агент этого во время задачи не делает.

Файлы тестов, этот отчёт и скрипты разработки остаются в репозитории. Runtime ZIP
получает модули `project_checks.py` и `fix_validation.py` автоматически существующим
сборщиком; тесты и evaluation в него не попадают. Изменять `run.sh` для C15 не нужно.
